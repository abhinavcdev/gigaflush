Every JavaScript package manager keeps a global cache of the packages it has downloaded, so the next install can skip the network. It's a good trade, until a few years of installs leave several gigabytes in a folder you've never looked at. Here's where each cache lives, how to measure it, and how to clear it without breaking anything.

<Callout type="note" title="Cache vs node_modules">
  The **cache** is one shared folder in your home directory. **node_modules** is a per-project copy installed from it. Clearing the cache doesn't shrink any project, and deleting `node_modules` doesn't touch the cache. They're two different piles. For the second one, see [how to delete all node_modules folders](/blog/delete-all-node-modules).
</Callout>

## Measure first

Ask each tool where its cache is, then check the size. Run only the lines for the package managers you use.

  client:visible
  id="where"

    { label: "macOS / Linux", code: "du -sh \"$(npm config get cache)\"\ndu -sh \"$(pnpm store path)\"\ndu -sh \"$(yarn cache dir)\"          # Yarn 1\ndu -sh ~/.bun/install/cache", note: "For Yarn 2 and later, use: yarn config get cacheFolder" },
    { label: "Windows (PowerShell)", code: "npm config get cache\npnpm store path\nyarn cache dir\n# Size of a folder:\n(Get-ChildItem -Recurse -Force \"$env:LOCALAPPDATA\\npm-cache\" | Measure-Object Length -Sum).Sum / 1GB", note: "Swap in the path each command prints." },
  ]}
/>

Typical locations, if you'd rather look in Finder or Explorer:

| Tool | macOS | Linux | Windows |
|---|---|---|---|
| npm | `~/.npm/_cacache` | `~/.npm/_cacache` | `%LocalAppData%\npm-cache` |
| pnpm | `~/Library/pnpm/store` | `~/.local/share/pnpm/store` | `%LocalAppData%\pnpm\store` |
| Yarn 1 | `~/Library/Caches/Yarn` | `~/.cache/yarn` | `%LocalAppData%\Yarn\Cache` |
| Yarn 2+ | `~/.yarn/berry/cache` | `~/.yarn/berry/cache` | `%LocalAppData%\Yarn\Berry\cache` |
| Bun | `~/.bun/install/cache` | `~/.bun/install/cache` | `%UserProfile%\.bun\install\cache` |

Paths change between versions and with your config, so trust the commands over the table.

## When you shouldn't clear it

- **Offline or on a slow connection.** The cache is what lets you install without the network. Clearing it before a flight is a bad idea.
- **To fix a broken install.** Corrupted caches are rare now. `npm cache verify` checks and repairs; reaching for `clean --force` first usually just costs you a re-download. Delete the project's `node_modules` and run `npm ci` instead, which reinstalls exactly what the lockfile pins.
- **On CI.** Most CI setups restore the cache deliberately to speed builds. Clearing it there makes every run slower.

<Callout type="tip" title="pnpm already saves you the most">
  pnpm installs each package version once into its store and hard-links it into every project, so ten projects using the same React don't hold ten copies. If you juggle many Node projects, switching to pnpm shrinks `node_modules` far more than clearing any cache. More on why in [why node_modules is so big](/blog/why-is-node-modules-so-big).
</Callout>

## The bigger pile is usually node_modules

Package caches top out at a few gigabytes. The `node_modules` folders in projects you stopped working on add up to far more, because each one is a full copy. Clear the cache for a quick win, then clear the old projects: run the commands in [our node_modules guide](/clean/node-modules), or scan your projects folder with Gigaflush and pick the ones to remove. Gigaflush handles project folders only; it never touches these global caches, so the commands above are still the way to clear them.
