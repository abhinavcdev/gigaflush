Every JavaScript framework drops its own hidden folder into your project: `.next`, `.nuxt`, `.svelte-kit`, `.turbo`, `.angular`. On top of that, tools write caches inside `node_modules`. Most are safe to delete, and knowing which saves you from hesitating the next time a build misbehaves or a disk fills up.

## The short answer

| Folder | Made by | Safe to delete? | What it costs |
|---|---|---|---|
| `.next` | Next.js | Yes | Next build is a full one; `.next/cache` (images, fetch, webpack/Turbopack) is lost |
| `node_modules/.vite` | Vite | Yes | Dependencies are pre-bundled again on next dev start |
| `node_modules/.cache` | babel-loader, webpack, ESLint, Storybook… | Yes | Slower first build or lint |
| `.turbo` | Turborepo | Yes | Local task cache gone; tasks run again once |
| `.nuxt`, `.output` | Nuxt | Yes | Regenerated by `nuxi dev` / `nuxi build` |
| `.svelte-kit` | SvelteKit | Yes | Regenerated by `svelte-kit sync` and dev/build |
| `.angular/cache` | Angular CLI | Yes | Slower next build; also `ng cache clean` |
| `.parcel-cache` | Parcel | Yes | Slower next build |
| `.astro` | Astro | Yes | Generated types; recreated on dev/build |
| `.eslintcache` | ESLint | Yes | Next lint checks every file |
| `dist`, `build` | Your build | Usually | Sometimes committed or published; check first |

None of these hold source code or settings you wrote by hand. Configuration lives in files like `next.config.js` and `vite.config.ts`, which stay put.

<Callout type="tip" title="The fix for 'it works after I deleted .next'">
  A stale build cache is behind a surprising number of "only on my machine" bugs: an old environment variable baked into a page, a renamed file still served, a dependency upgrade that doesn't seem to apply. Deleting the framework folder and restarting the dev server is a cheap first step before deeper debugging.
</Callout>

## Which are actually big?

On disk, the order is nearly always the same:

1. **`node_modules`** itself, by a wide margin. Everything inside it, including `.cache` and `.vite`, goes with it.
2. **`.next`** in a large Next.js app, especially with image optimization: `.next/cache` can reach several gigabytes.
3. **`.turbo`** in monorepos that run many tasks.
4. The rest are usually tens of megabytes.

So for disk space, the folders worth clearing are `node_modules` and `.next` in projects you aren't actively working on. In a project you're building every day, leave the caches alone: they're what makes your builds fast.

## Clearing across all your projects

Doing this one project at a time is fine for a broken build, and tedious for a full disk. Gigaflush scans a folder for `node_modules` next to a `package.json` (which takes every `.cache` and `.vite` inside with it) and lists them by size so you can remove the ones from old projects. It deliberately skips generic names like `dist`, `build` and `.next`, since those aren't always disposable; the commands above handle them.
